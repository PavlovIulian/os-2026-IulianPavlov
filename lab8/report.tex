\section{Theoretical Background and Objectives}

\subsection{Laboratory Objectives and Scope}
In Laboratory Work No.~7, the core process management primitives (\texttt{fork}, \texttt{exec}, and \texttt{wait}) were explored within a standard Linux user-space environment. In Laboratory Work No.~8, we transition these exact fundamental concepts into xv6---the teaching operating system running on RISC-V.

Inside xv6 there is no glibc, no \texttt{strace}, and no dynamic linking: only the bare-metal kernel system calls declared directly in \texttt{user/user.h}. The objectives of this laboratory are:
\begin{itemize}
    \item \textbf{Process Lifecycle in xv6 (\texttt{run.c})}: Implementing the classic shell sequence (\texttt{fork()}, \texttt{exec()}, \texttt{wait()}) to execute user binaries (\texttt{echo}, \texttt{ls}), capturing exit statuses, and observing execution failure paths.
    \item \textbf{Comparing Linux vs.~xv6 Primitives}: Analyzing the direct parallels between POSIX system calls on Linux and native xv6 system calls.
    \item \textbf{Bidirectional IPC Coordination (\texttt{pingpong.c})}: Coordinating two processes via two distinct anonymous pipes to exchange a byte back and forth without data races or self-reading.
    \item \textbf{Concurrent Prime Sieve (\texttt{primes.c} -- Optional)}: Implementing Doug McIlroy's concurrent prime sieve pipeline, chaining dynamically created filter stages connected by anonymous pipes.
    \item \textbf{Identifying Kernel Resource Bottlenecks}: Exploring system-wide open file table limits (\texttt{NFILE = 100}) and per-process descriptor limits (\texttt{NOFILE = 16}).
    \item \textbf{Argument Passing (\texttt{xargs.c} -- Stretch Goal)}: Building \texttt{user/xargs.c} to consume newline-separated inputs and execute target programs with composite argument vectors using \texttt{fork()}, \texttt{exec()}, and \texttt{wait()}.
\end{itemize}

\subsection{Internal xv6 Pipe Architecture}
In xv6 (\texttt{kernel/pipe.c}), an anonymous pipe is implemented as a bounded in-memory FIFO ring buffer:
\begin{lstlisting}[style=cstyle]
struct pipe {
  struct spinlock lock;
  char data[PIPESIZE]; // 512 bytes
  uint nread;          // number of bytes read
  uint nwrite;         // number of bytes written
  int readopen;        // read fd is still open
  int writeopen;       // write fd is still open
};
\end{lstlisting}

\begin{itemize}
    \item \textbf{Synchronization}: When \texttt{read()} finds the buffer empty (\texttt{nread == nwrite}) and the write end remains open (\texttt{writeopen != 0}), the kernel calls \texttt{sleep(\&pi->nread, \&pi->lock)} to suspend the reader. When a writer issues \texttt{write()}, it appends data and calls \texttt{wakeup(\&pi->nread)}, moving sleeping readers to the \texttt{RUNNABLE} state.
    \item \textbf{EOF Generation}: When a process calls \texttt{close()} on the write end of a pipe, \texttt{pipeclose()} sets \texttt{writeopen = 0} and wakes any sleeping readers. If the buffer is empty and \texttt{writeopen == 0}, \texttt{piperead()} immediately returns \texttt{0}, signaling End-Of-File.
\end{itemize}

\section{Part 1: Process Lifecycle inside xv6 (\texttt{run.c})}

\subsection{Implementation Details}
We developed \texttt{user/run.c} to replicate the fundamental three steps of a shell directly inside xv6:
\begin{enumerate}
    \item \texttt{fork()} to duplicate the process and produce a child.
    \item \texttt{exec()} inside the child to become \texttt{echo}.
    \item \texttt{wait()} inside the parent to await child termination and collect its exit status.
\end{enumerate}

\begin{lstlisting}[style=cstyle]
#include "kernel/types.h"
#include "user/user.h"

// the three steps of the shell, inside xv6: echo hello from the child
int
main(int argc, char *argv[])
{
  printf("parent: my pid is %d\n", getpid());

  int pid = fork(); // step 1: copy myself
  if(pid < 0){
    printf("fork failed\n");
    exit(1);
  }

  if(pid == 0){ // only the child runs this
    printf("child: my pid is %d\n", getpid());
    char *args[] = { "echo", "hello", "from", "the", "child", 0 };
    exec("echo", args);
    printf("exec failed\n");
    exit(1);
  }

  int status;
  wait(&status);
  printf("parent: child %d ended with status %d\n", pid, status);
  exit(0);
}
\end{lstlisting}

\subsection{Answers to Questions (Observe -- Part 1)}
\begin{enumerate}
    \item \textbf{Write the three calls that \texttt{run.c} uses in xv6 and the three calls \texttt{run.c} used on Linux in Lab 7. What is the same?}
    \begin{itemize}
        \item \textbf{xv6 (\texttt{run.c})}: \texttt{fork()}, \texttt{exec()}, \texttt{wait(\&status)}.
        \item \textbf{Linux (\texttt{myrun.c})}: \texttt{fork()}, \texttt{execvp()} (or \texttt{execve()}), \texttt{waitpid(pid, \&status, 0)}.
        \item \textbf{What is the same}: The core Unix process management lifecycle is identical: \texttt{fork} clones the process, \texttt{exec} replaces process memory with a new binary, and \texttt{wait} blocks the parent until the child terminates and reports its exit code.
    \end{itemize}

    \item \textbf{Who prints ``hello from the child'': the code of \texttt{run}, or \texttt{echo}?}
    \textbf{\texttt{echo}} prints it.  
    When \texttt{exec("echo", args)} succeeds, the memory image of \texttt{run} in the child is completely overwritten by \texttt{/echo}. The instructions following \texttt{exec} in \texttt{run.c} never run. Control begins at \texttt{main()} in \texttt{echo.c}, which writes its arguments to standard output.

    \item \textbf{Why is the status 1 here and 127 on Linux?}
    The exit status collected by \texttt{wait()} is simply the integer passed to \texttt{exit()}:
    \begin{itemize}
        \item In xv6 \texttt{run.c}, the failure branch calls \texttt{exit(1)}, yielding status 1.
        \item On Linux in Lab 7 (\texttt{myrun.c}), the failure branch called \texttt{exit(127)} (the standard POSIX convention for command not found), yielding status 127.
    \end{itemize}
\end{enumerate}

\section{Part 2: Ping-Pong Communication (\texttt{pingpong.c})}

\subsection{Implementation Details}
We implemented \texttt{user/pingpong.c}. The parent sends a byte to the child through pipe \texttt{p2c}. The child reads it, prints its own PID, sends the byte back through pipe \texttt{c2p}, and terminates. The parent reads from \texttt{c2p}, prints its own PID, and reaps the child:

\begin{lstlisting}[style=cstyle]
#include "kernel/types.h"
#include "user/user.h"

int
main(int argc, char *argv[])
{
  int p2c[2], c2p[2];
  char b = 'x';

  if(pipe(p2c) < 0 || pipe(c2p) < 0){
    fprintf(2, "pingpong: pipe failed\n");
    exit(1);
  }
  if(fork() == 0){
    close(p2c[1]); /* child does not write to p2c */
    close(c2p[0]); /* child does not read from c2p */
    if(read(p2c[0], &b, 1) != 1)
      exit(1);
    printf("%d: received ping\n", getpid());
    write(c2p[1], &b, 1);
    close(p2c[0]);
    close(c2p[1]);
    exit(0);
  }
  close(p2c[0]); /* parent does not read from p2c */
  close(c2p[1]); /* parent does not write to c2p */
  write(p2c[1], &b, 1);
  read(c2p[0], &b, 1);
  printf("%d: received pong\n", getpid());
  close(p2c[1]);
  close(c2p[0]);
  wait(0);
  exit(0);
}
\end{lstlisting}

\subsection{Execution Trace}
We launched xv6 under QEMU and verified execution:
\begin{lstlisting}[style=consolestyle]
$ pingpong
4: received ping
3: received pong
\end{lstlisting}
The child's \texttt{"received ping"} output arrives strictly before the parent's \texttt{"received pong"}.

\subsection{Answers to Questions (Observe -- Part 2)}
\begin{enumerate}
    \item \textbf{Why do you need TWO pipes, and not one shared by both directions?}  
    Pipes in UNIX and xv6 are strictly unidirectional. A pipe has a single shared kernel ring buffer. If a single pipe were used for both directions, the parent would race against the child after writing and would immediately read back its own byte before the child ever ran. Two distinct pipes provide isolated unidirectional channels.

    \item \textbf{Nothing in your code says ``wait until the child has replied''. What makes the parent wait?}  
    The blocking synchronization semantics of \texttt{read(c2p[0], \&b, 1)} make the parent wait. Because the buffer is empty and the child holds an open write descriptor, the kernel suspends the parent via \texttt{sleep(\&pi->nread, \&pi->lock)} until the child calls \texttt{write()} and triggers \texttt{wakeup()}.
\end{enumerate}

\section{Part 3: Concurrent Prime Sieve (\texttt{primes.c} -- Optional)}

\subsection{Design and Implementation}
Doug McIlroy's concurrent prime sieve generates numbers $2 \dots 35$ into a pipeline of filter stages:
\begin{lstlisting}[style=cstyle]
#include "kernel/types.h"
#include "user/user.h"

#define LIMIT 35

void stage(int) __attribute__((noreturn));

void
stage(int in)
{
  int p, n, fd[2], pid;

  if(read(in, &p, sizeof(p)) != sizeof(p)){
    close(in);
    exit(0);
  }
  printf("prime %d\n", p);

  if(pipe(fd) < 0){
    printf("primes: pipe failed after prime %d\n", p);
    close(in);
    exit(1);
  }
  pid = fork();
  if(pid < 0){
    printf("primes: fork failed after prime %d\n", p);
    close(fd[0]); close(fd[1]); close(in);
    exit(1);
  }
  if(pid == 0){
    close(fd[1]); close(in);
    stage(fd[0]);
  }
  close(fd[0]);
  while(read(in, &n, sizeof(n)) == sizeof(n)){
    if(n % p != 0)
      write(fd[1], &n, sizeof(n));
  }
  close(in);
  close(fd[1]);
  wait(0);
  exit(0);
}

int
main(int argc, char *argv[])
{
  int fd[2];
  if(pipe(fd) < 0) exit(1);
  if(fork() == 0){
    close(fd[1]);
    stage(fd[0]);
  }
  close(fd[0]);
  for(int i = 2; i <= LIMIT; i++)
    write(fd[1], &i, sizeof(i));
  close(fd[1]);
  wait(0);
  exit(0);
}
\end{lstlisting}

\subsection{Execution Trace and Resource Analysis}
\begin{lstlisting}[style=consolestyle]
$ primes
prime 2
prime 3
prime 5
prime 7
prime 11
prime 13
prime 17
prime 19
prime 23
prime 29
prime 31
\end{lstlisting}

\textbf{Resource Bottleneck at Limit 280}: Raising the limit to 280 causes execution to fail at prime 227 with \texttt{primes: pipe failed after prime 227}. This occurs because xv6 allocates two global file slots in \texttt{ftable} for every pipe, reaching the system-wide limit \texttt{NFILE = 100} in \texttt{kernel/param.h}.

\section{Conclusions}

\begin{enumerate}
    \item \textbf{Process Lifecycle Parallels}: Implementing \texttt{run.c} confirmed that \texttt{fork()}, \texttt{exec()}, and \texttt{wait()} operate identically in xv6 and Linux.
    \item \textbf{Pipe Discipline}: Verified that bidirectional IPC requires two independent pipes to avoid data races and self-consumption, with synchronization mediated by blocking \texttt{read()}.
    \item \textbf{Pipeline Concurrency}: Doug McIlroy's prime sieve demonstrated stream-based parallelism where processes execute concurrently across pipeline stages.
    \item \textbf{Kernel Resource Constraints}: Identified the system-wide file table limit (\texttt{NFILE = 100}) as the primary bottleneck in deep process pipelines.
\end{enumerate}
