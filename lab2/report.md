### 2. Which two OS features must exist for a pipe (`|`) to work?
When executing `$ ls | grep c` inside xv6, the pipe connects the standard output of `ls` to the standard input of `grep`. For this mechanism to function, the operating system must provide:

1. **Concurrent Process Execution and Isolation (`fork()` / Process Management):**
   - The OS must support creating and running at least two independent processes simultaneously.
   - Each process runs in its own private virtual address space with its own file descriptor table.

2. **Inter-Process Communication (IPC) via Shared Kernel Buffering (`pipe()`, `dup()`, and File Descriptors):**
   - The OS must provide a kernel-managed, unidirectional FIFO byte-stream buffer.
   - The OS must support file descriptor duplication/redirection (`dup()` / `close()` in user space) so that the write end of the pipe replaces descriptor 1 (`stdout`) of the producer (`ls`), and the read end replaces descriptor 0 (`stdin`) of the consumer (`grep`).
   - The kernel scheduler must coordinate synchronization: blocking the reader when the buffer is empty, and blocking the writer when the buffer is full.

## Part 3: Source Reading & "The Big Idea" Box Answers

### 1. Architectural Separation: `kernel/` versus `user/`
The xv6 source tree cleanly divides into two primary directories, reflecting the fundamental hardware privilege boundary of modern computer architecture:

- **`kernel/` (Privileged / RISC-V Supervisor Mode - S-mode):**
  - Contains the core operating system: process scheduler (`proc.c`), virtual memory/page table management (`vm.c`), trap and interrupt dispatchers (`trap.c`, `trampoline.S`), file system implementation (`fs.c`, `bio.c`, `sysfile.c`), and hardware drivers (UART, virtio disk).
  - Code in `kernel/` executes with full CPU privileges, allowing direct interaction with physical memory, page table registers (`satp`), interrupt enable registers (`sstatus`, `sie`), and memory-mapped hardware devices.

- **`user/` (Unprivileged / RISC-V User Mode - U-mode):**
  - Contains standard userland utilities (`cat.c`, `ls.c`, `sh.c`, `echo.c`, `sleep.c`) and user libraries (`ulib.c`, `printf.c`, `umalloc.c`).
  - Programs in `user/` run in isolated virtual address spaces. They cannot directly access hardware, manipulate page tables, or access kernel memory; any attempt to execute privileged instructions raises an exception.

---

### 2. System Calls vs. Ordinary Functions
In `user/cat.c`:
```c
while ((n = read(fd, buf, sizeof(buf))) > 0) {
  if (write(1, buf, n) != n) { ... }
}
```
- `read()` and `write()` are **not** ordinary C functions whose bodies execute within the caller's stack frame.
- They are **system call stubs** auto-generated by `user/usys.pl` into assembly (`usys.S`).
- When called, the stub loads the system call number (e.g., `SYS_read` or `SYS_write` from `kernel/syscall.h`) into register `a7` and executes the RISC-V `ecall` (environment call) instruction.
- The `ecall` hardware instruction transitions the CPU from User mode to Supervisor mode, causing a trap handled by `kernel/trampoline.S` and `kernel/trap.c`.
- The kernel's `syscall()` dispatcher in `kernel/syscall.c` reads the syscall number from the process trapframe, retrieves arguments safely from user memory, and invokes the kernel implementation (`sys_read()` or `sys_write()` in `kernel/sysfile.c`).
- Once finished, the return value is placed in trapframe register `a0`, and `sret` returns execution to User mode.

---

### 3. "The Big Idea" Reflection
> *On Linux (Lab 1), developers and users interact with the system solely from user space through POSIX library wrappers and external observation tools (`strace`, `/proc`, `/sys`). In xv6, because the entire kernel is approximately 9,000 lines of clean ANSI C, we have total visibility into **both** sides of the system call boundary: the user program that requests a service (`user/`) and the exact kernel routines that execute it (`kernel/`). This makes it possible to understand every layer of operating system mechanics in detail.*

## Part 4: Implementation Notes for `user/sleep.c`

### 1. Requirements & Logic
- **Argument Verification:** Inspect `argc`. If `argc != 2`, write error message `"usage: sleep <ticks>\n"` to file descriptor 2 (`stderr`) and exit with status 1.
- **Duration Conversion:** Parse `argv[1]` to an integer using `atoi()`.
- **System Call Invocation:** Invoke the kernel timer pause system call to pause the process for the specified number of clock ticks.
- **Clean Exit:** Call `exit(0)` to terminate normally.

### 2. Note on `sleep()` vs. `pause()` Naming
In the classic xv6 documentation, the system call is called `sleep(int)`. However, in MIT's upstream `xv6-riscv` repository (updated in August 2025):
- The user-space system call prototype was renamed to `int pause(int);` in `user/user.h` and `kernel/syscall.h` (`SYS_pause`).
- This change prevents naming collisions with the internal kernel synchronization primitive `void sleep(void *chan, struct spinlock *lk)` defined in `kernel/proc.c`.
- Our implementation in `user/sleep.c` invokes `pause(atoi(argv[1]))`, perfectly integrating with the current xv6 kernel.

### 3. Build & Test Verification
- **Makefile entry:** Registered in `UPROGS` under `Makefile`:

  ```makefile
  UPROGS=\

      $U/_sleep\

  ```
- **Test cases executed in QEMU:**

  - `$ sleep`: Emits `usage: sleep <ticks>` to descriptor 2 and terminates with error code 1.
